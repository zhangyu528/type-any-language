## 0. 设计任务定位

本文档是**正式 UX/UI 设计任务的输入**。它解决一件事：

**让设计师在没有任何预设的前提下，自由决定这个产品的视觉与交互。**

> **本文不写**：产品功能（见 PRD.md）、API 路径、代码细节、组件库选型。
>
> **本文不预设**：设计方向、色彩、字体、间距、动效曲线、视觉层次、布局骨架。这些全部由设计师提案。

---

## 1. 设计师自由发挥空间

**除了硬约束（第 2 章）和反模式（第 3 章），一切由设计师决定。**

设计师可以：

- 选择任何设计方向（极简、印刷感、夜色、纸质、复古、未来、抽象等任意风格）
- 选择任何色彩体系（不限色相、不限数量、不限饱和度）
- 选择任何字体（衬线、无衬线、等宽、手写体、装饰体等任意）
- 选择任何节奏骨架（不限栅格、不限最大宽、不限卡片尺寸）
- 选择任何动效（弹性、缓动、瞬切、组合等任意）
- 选择任何组件策略（自建、Radix Primitives 等）；具体库选型见 §2.3 的硬约束

**设计师提案时不需要证明"为什么不是另一种"**。只需要让自己的提案**自洽**。

## 2. 硬约束（不可妥协）

只有以下内容是硬约束。其他都是建议。

### 2.1 产品语境（来自 PRD）

设计师必须理解并尊重：

| 语境 | 含义 |
|---|---|
| **核心场景** | 用户在听一段英文音频后，逐字敲出完整句子 |
| **使用频率** | 每天 20-30 分钟，连续 30+ 天是常见模式 |
| **唯一练习模式** | 只有"听音写句"，不引入其他游戏化机制 |
| **三种用户状态** | 游客 / 学习者 / 回头学习者——同一套 UI 应能温和容纳 |

### 2.2 可访问性（WCAG）

| 项 | 标准 |
|---|---|
| **颜色对比度（正文）** | ≥ 4.5:1（WCAG AA） |
| **颜色对比度（大字）** | ≥ 3:1（WCAG AA Large） |
| **焦点指示** | 永久可见；不被覆盖 |
| **触控目标** | ≥ 44×44（WCAG 2.5.5） |
| **链接命中区** | ≥ 24×24（WCAG 2.5.8） |
| **键盘可达** | 所有交互元素可 Tab |
| **减弱动效** | `prefers-reduced-motion: reduce` 必须被尊重 |
| **屏幕阅读器** | 模态 `role="dialog"`；装饰动画 `aria-hidden` |

### 2.3 响应式断点（仅作参考，设计师可调整）

- 移动端：≤640px
- 平板：640-1024px
- 桌面：>1024px

断点之间的布局策略、卡片堆叠方式、字号缩放规则由设计师定。

### 2.4 组件库选型（设计师需说明理由）

设计师选择组件库策略时，应当在交付物中说明：

- 哪些组件自建（理由：自建颗粒度更细、视觉更统一）
- 哪些用 Radix Primitives（理由：需要复杂交互但不想自己处理 a11y）
- 是否引入第三方 UI 库（理由：节省时间或获得特定能力）

**任何引入的第三方库必须通过 §3 反模式的过滤**——例如：若某库的招牌组件是"持续闪烁 / 渐变动画"等反模式，则**不引入**该库，无论其他组件多好用。

## 3. 动效是产品的核心交互反馈

> ⚠️ **重要前提**：本产品的练习循环（听音写句）**完全依赖即时视觉反馈**——用户每敲一个字符，需要立刻看到"对 / 错"的视觉变化；切到下一题，需要有过渡维持位置感；命中目标，需要有过渡传达达成感。
>
> **没有动效 = 没有反馈 = 没有产品。**
>
> §3.1-§3.3 列出的"反模式"，**不是反对动效**，是反对**某些会破坏产品体验的具体动效形态**。设计师应当提供**丰富、克制、有意义**的动效，而不是少动效或无动效。

### 3.1 反模式：干扰专注的动效

❌ 这些动效**会破坏**用户的深度专注，**反对**：

| 反模式 | 为什么反对 |
|---|---|
| 持续闪烁 / 渐变动画 | 持续消耗认知资源，与"专注型产品"对立 |
| 鼠标跟随光晕 | 把用户注意力从"听"拉向"鼠标位置" |
| 3D 倾斜卡片 | 鼠标移动触发倾斜，分散注意力 |

✅ 设计师**应该做**的同类动效（举例）：

- 字符输入的即时颜色反馈（短促、稳定、不持续）
- 当前播放按钮的脉冲指示（只在播放时存在，暂停即停）
- 焦点环的出现（用户主动操作时）

### 3.2 反模式：廉价感的动效

❌ 这些动效**显廉价**，**反对**：

| 反模式 | 为什么反对 |
|---|---|
| 每题答对都撒花 / emoji 庆祝 | 3 题后用户麻木，庆祝失去意义 |
| 强 shake / 闪烁作为错误警告 | 像在羞辱用户，而非温柔提示 |
| 多个动效在同一时刻同一区域叠加 | 视觉噪声，廉价感 |
| 弹窗出现时再嵌套弹窗动效 | 视觉混乱 |

✅ 设计师**应该做**的同类动效（举例）：

- 字符错误时的轻位移 + 颜色过渡（横向 ≤ 4px，200ms 内完成）
- 切到下一题的过渡（保持用户的"位置感"，不是消失再出现）
- 命中重要时刻（首次达成 7/30/100 天）的克制庆祝（戏剧性但不夸张）

### 3.3 反模式：阻断沉浸的动效

❌ 这些动效**打断用户的心理连续性**，**反对**：

| 反模式 | 为什么反对 |
|---|---|
| 切路由时整屏淡出再淡入 | 用户感觉"页面消失了"，失去位置感 |
| 顶部红色横条提示错误 | 强制从主区抢注意力 |
| 模态出现时整屏蒙黑 | 蒙黑 = 打破空间感 |
| CTA 入场用大位移弹性 | 喧宾夺主，主角应是内容 |

✅ 设计师**应该做**的同类动效（举例）：

- 路由切换时背景保持不变（"切换路由 ≠ 切换世界"）
- 错误提示浮在出错字段下方（不抢主区焦点）
- 模态出现时背景轻模糊（不是蒙黑）
- CTA 入场用轻浮起（让位给内容）

### 3.4 设计师应思考的动效维度

设计师提案时，应当为以下每种**交互时刻**给出具体的动效规范：

| 交互时刻 | 动效需要回答的问题 |
|---|---|
| **字符输入反馈** | 对 / 错 / 当前格 vs 标准 各自的视觉过渡是什么？ |
| **题目切换** | 切到下一题的过渡如何维持"位置感"？ |
| **音频播放状态** | 播放中 / 暂停 / 倍速切换 各自的视觉指示是什么？ |
| **模态出现 / 关闭** | 模态的入场和退场节奏如何与背景层协调？ |
| **路由切换** | 切路由时背景层是否保持？内容层如何过渡？ |
| **进度推进** | 日标环、日历填充、KPI 数字 如何"自然地"推进？ |
| **庆祝触发** | 命中日目标 / 连续 +1 / 首次达成 N 天 的庆祝强度如何分级？ |
| **错误反馈** | 字段错误 / 网络断 / 表单校验失败 各自的反馈节奏是什么？ |
| **状态切换** | 暗色模式 / 主题切换的过渡节奏是什么？ |
| **响应 prefers-reduced-motion** | 减弱动效下，每种交互如何"降级"？ |

### 3.5 通用原则（适用于所有动效）

| 原则 | 含义 |
|---|---|
| **每个动效都有意义** | 不要装饰性动效；如果只是"为了好看"，删掉 |
| **每个动效都有节奏** | 同一时刻同一区域只有一种动效在发生 |
| **动效跟随用户操作** | 用户主动操作触发的动效 = 反馈；自动播放的动效 = 噪声 |
| **减弱动效必须可用** | `prefers-reduced-motion: reduce` 下，应用必须仍然完整可用 |

## 4. 设计师交付物清单

设计方应当输出：

1. **设计方向陈述**（1-2 页）：你选择的设计方向是什么，为什么适合这个产品
2. **视觉语言定义**：色板（含明暗）、字体（含正文字号阶梯）、节奏骨架、留白规则
3. **核心交互状态机**：登录页提交、练习切题、错误反馈、庆祝触发、模态打开关闭
4. **关键页面线框图**：Landing / Dashboard / Practice / Me / Login / Signup
5. **设计 token 草案**：可由前端直接落地的 CSS variables 或 JS 常量
6. **组件清单**：哪些组件自建、哪些用 Radix Primitives、是否引入第三方库（及理由）
7. **暗色主题映射**：明暗对照表
8. **动效规范**：每种交互的具体曲线参数（stiffness / damping / duration）
9. **可访问性自查报告**：键盘可达路径、屏幕阅读器测试、对比度测试结果

## 5. 验收问题清单

设计方交付时，应当能回答：

| 维度 | 验收问题 |
|---|---|
| **方向自洽** | 设计师的方向陈述、视觉语言、交互状态、组件清单是否构成统一的系统？ |
| **产品契合** | 设计是否与"听音写句 + 深度专注 + 每天使用"的产品语境契合？ |
| **键盘可达** | keyboard-only 能否完成"打开 / 选库 / 练习一题 / 注册"？ |
| **减弱动效** | `prefers-reduced-motion: reduce` 下体验是否仍然可用？ |
| **暗色完整** | 暗色主题是否独立、完整，不只是"反转"？ |
| **跨设备一致** | 移动 / 平板 / 桌面三档是否都体现了设计方向，不是简单缩放？ |
| **空态 / 错误态** | 空态、错误态、加载态是否都经过设计（而非用占位文字糊弄）？ |
| **第三方依赖** | 如果用了第三方库（shadcn / react bits / Radix 等），是否说明了为什么？ |
